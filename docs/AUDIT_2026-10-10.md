# Audit — 2026-10-10

A static + dynamic audit of the **uncommitted work on top of `28dfaea`**, run before it is
committed. Two changes are under review:

* **A module split of the largest source files, with no behavior change intended.**
  `gui.rs` (7,466 lines), `ui.rs`, `vault.rs`, `records.rs`, `storage.rs` and the desktop
  `lib.rs` were split into submodules by screen and responsibility (`gui/`, `vault/`,
  `records/`, `storage/`, and `clipboard.rs` / `prefs.rs` / `export_dir.rs`). Every moved
  item was moved verbatim by a script. The only intended code edits are added `pub(super)`
  visibility, module wiring, and one `include_bytes!` path that moved one directory deeper.
* **Removal of the terminal UI (`vaultis --tui`, `ui.rs`, ~4,500 lines).** The GUI already
  covered every TUI action, so nothing was ported. ratatui was dropped. The CLI's no-echo
  password prompt now uses `crossterm` directly (the same 0.29.0 that ratatui re-exported).
  `--tui` is now refused with a pointer to its replacement in both binaries, and a
  `--no-default-features` build refuses an interactive launch.

**Threat model:** unchanged from [`THREAT_MODEL.md`](THREAT_MODEL.md). In scope: theft of or
tampering with the on-disk vault files, a crafted vault, a hostile merge source, malicious
paths, filenames and record content, a local multi-user filesystem, and secrets lingering in
memory or on disk. Out of scope: network attacks, and an attacker already running as the
user with the vault unlocked in RAM.

**What this round deliberately went after that the last one did not.** The 2026-09-16 round
audited new *behavior*. This round audits a change that claims to have *no* behavior change,
across 10,000 lines. Two questions follow from that:

1. **Is the split really a pure move?** In particular, did any formerly private item become
   reachable from outside its crate through the new `pub use module::*` re-exports? That
   would widen the attack surface of the audited core.
2. **Does removing an entire front-end change any secret path or any gate?** That covers the
   password prompt's terminal handling, the clipboard helpers that were folded into the GUI,
   the read-only gate, and the dependency tree.

**Result: two Low findings, both pre-existing, both fixed. Nothing in the reviewed change is
a defect.** The split is a verified pure move. The public API of `vaultis-core` and
`vaultis-ffi` is identical item for item. The TUI removal changed exactly the surface it
meant to and shrank the supply chain by 79 crates. Both findings came from looking hard at
untested corners next to the change:

* **A-1:** the console binary's `--write` decision, the first step of the read-only gate,
  had no test. Mutation testing proved that inverting it passes the whole suite.
* **A-2:** the memory-residue harness that the deep audit relies on loses its child process
  whenever a scan takes over 60 seconds, which is always the case under ASan. Its own
  negative control caught this, so the result could not have read as a false pass.

## Findings

### A-1 — the console binary's `--write` check had no test (Low, read-only gate / test coverage)

`crates/vaultis-desktop/src/main.rs` (`main`)

**What the code does.** The console binary decided writability inline:

```rust
let writable = args.iter().any(|a| a == "--write");
```

The windowed binary makes the same decision in `launch::resolve_interactive`, which is
tested both ways. The console binary's copy is only consumed by `gui::run`, which no test can
reach without a display.

**What it must do.** Be observable by a test. This is the first decision of the read-only
gate, and `docs/THREAT_MODEL.md` relies on read-only being the default.

**The concrete input that separates them.** `cargo mutants` replaced `==` with `!=` on that
line (`main.rs:328`). The mutated binary opens **every** interactive launch writable unless
`--write` is the only argument, and **all 265 desktop tests passed**: `MISSED main.rs:328:42:
replace == with != in main`. The shipped code is correct (verified by reading). Nothing
would have caught a regression.

**Severity: Low, and why.** No defect ships. It is filed because the uncaught regression is
a read-only-gate bypass, and because it is this codebase's signature guard asymmetry, applied
to test coverage this time: the windowed binary's identical decision was tested and the
console binary's was not. The line predates this round. It surfaced only because the round's
diff touched the comment above it.

**Fix applied.** `launch::wants_write(&[String]) -> bool`, now the single place either binary
decides writability. `resolve_interactive` and `main` both call it, in the same spirit as the
module's existing "both binaries resolve identically" rule.

**Regression test.** `launch::tests::wants_write_is_true_only_for_the_exact_write_flag` covers
empty args, a bare DIR, a subcommand, the near-misses `--writ`, `--write=yes`, `-w` and
`--WRITE`, and `--write` in each position. **Mutation check after the fix:** `cargo mutants -F wants_write` — **3 mutants, 3
caught** (`-> true`, `-> false`, `==`→`!=`). The decision that used to survive inversion can
no longer change without failing a test.

### A-2 — the memory-residue harness loses its child whenever a scan is slow (Low, test instrument)

`crates/vaultis-core/tests/memory_residue.rs` (`measure`)

**What the code does.** The parent reads the child's stdout until `READY`, then drops the
reader:

```rust
let out = BufReader::new(ch.stdout.take().expect("child stdout"));
for line in out.lines().map_while(Result::ok) { if line.starts_with("READY") { …; break; } }
```

`lines()` consumes the reader, and `break` drops it, which closes the pipe. If the scan then
takes longer than 60 seconds, the child's libtest prints `has been running for over 60
seconds` into the closed pipe. Rust ignores SIGPIPE, so the `println!` panics and **the
child exits mid-scan**. From then on every read of `/proc/<pid>/mem` returns EOF, which the
scanner counts as "nothing found".

**What it must do.** Photograph a live child for the whole scan.

**The concrete input that separates them.** Under ASan the scan of ~320 MiB is slow, and the
`hold` control (vault open, secrets legitimately live) reported **0 / 0**:

```
residue[hold]: master-password 0 hit(s), record-field 0 hit(s), across 262144000 bytes …
CONTROL FAILED: the scanner could not find sentinels that are still LIVE …
```

The diagnosis was established three ways:

* An independent Python scan of a live ASan child in `hold` mode, with its stdout kept open,
  found **4 / 2** — the July baseline exactly.
* `strace` of the harness showed 220 full reads followed by **439 zero-byte reads** (EOF),
  starting mid-scan and continuing through the heap where the sentinels live.
* A direct test: with stdout kept open, the child is alive after 70 s. With stdout closed
  after `READY`, it is **dead with exit code 101**.

TSan reproduced the same control failure independently.

**Severity: Low, and why.** It is a test-instrument defect, not a product defect. No user is
exposed, and the harness's negative control did exactly its job: it refused to report a
meaningless "clean" result. It is filed because the residue test is the *only* observation
of the "secrets are wiped on drop" claim, and it had silently become unusable under the
sanitizers. Those are the instruments that make residue visible, and D-1 is tracked with them.
It stayed hidden whenever a scan finished in under 60 seconds, which explains how the July
run passed.

**Fix applied.** The reader is kept alive until the scan is over, and drained before the
child is reaped. A new assertion, `matches!(ch.try_wait(), Ok(None))` after every scan, makes
a child that dies mid-scan fail loudly with the real cause instead of masquerading as a
control failure, or as a clean result.

**Verified after the fix** (`docs/AUDIT_2026-10-10_deep.md` has the full tables). Under
ASan the run took 890 s, far past the 60 s point that used to kill the child, and the result
is `hold` **4 / 2**, with D-1's **3** master-password copies at every dropped stage and **0**
record-field copies, identical to July. Under TSan: `hold` **1 / 2**, passing. Under a normal
allocator: `hold` **1 / 2**, every dropped stage **0 / 0**, passing.

## Leads chased and refuted

* **Did the split widen the public API?** No. `cargo public-api` against a git worktree of
  `28dfaea`: `vaultis-core` exposes the **same 742 public items**, compared as sets because
  the several `impl OpenVault` blocks only reorder the listing. `vaultis-ffi` is
  **identical**. The desktop library changed by exactly the intended three items: `ui` and
  `ui::run` removed, `launch::TUI_REMOVED` added. Inside each crate, `pub(super)` in
  `vault/x.rs` reaches exactly what "private in `vault.rs`" reached before (the `vault`
  module and its descendants), so effective visibility is unchanged as well.
* **Is the split really a pure move?** Yes. A line-multiset diff of each original file
  against its split modules, ignoring only added `pub(super)`, comments and module wiring,
  is **empty** for `vault`, `records`, `storage`, `merge`, `csv`, the core `lib.rs` and
  `vault/migrate.rs`. For the GUI the only code differences are the `include_bytes!` path
  (one directory deeper) and `format_time` arriving from the removed `ui.rs`. `crypto.rs`,
  `password.rs`, `types.rs`, `fault.rs`, `proofs.rs` and `single_instance.rs` were not
  touched.
* **Did folding the shared helpers into the GUI change a secret path?** No. `presize_secret`,
  `clear_clipboard`, `label_list` and `same_vault_path` in `gui/` are byte-for-byte the
  versions `gui.rs` shipped at `28dfaea`. They were taken from that revision, not from the
  TUI's copies.
* **Did the password prompt change?** No. `read_line_no_echo` is identical apart from its
  `use` path. `ratatui::crossterm` and `crossterm` resolve to the same crate: there is
  exactly one `crossterm` in the lock file, 0.29.0. The raw-mode restore guard is untouched.
* **Can `--tui` slip past the refusal into a subcommand?** No. `main` refuses it after flag
  extraction and before dispatch, so `vaultis decrypt --tui` exits non-zero without
  prompting. Tested by `the_removed_tui_flag_is_refused_with_a_pointer_to_its_replacement`.
  The windowed binary refuses it too (`the_windowed_binary_refuses_the_removed_tui_flag_too`),
  so `vaultis DIR --tui` and `vaultis-gui DIR --tui` cannot diverge.
* **Does any shipped launcher pass `--tui` and now fail at startup?** No. The Windows
  shortcuts pass only `--write` (`make-shortcuts.ps1`), the Linux `.desktop` files pass
  nothing or `--write`, and the macOS bundle launches `vaultis-gui`. Only the build scripts'
  printed hints mentioned `--tui`, and those were updated.
* **Did the supply chain change in any way other than shrinking?** No. 79 packages left
  `Cargo.lock`, **none were added, and no version changed**. `fuzz/Cargo.lock` is unchanged.
  `deny.toml` has no entry tied to a removed crate.
* **Did the GUI glyph test keep its coverage?** It would not have. It scanned
  `include_str!("gui.rs")`, which after the split is about a fifth of the GUI. Fixed in the
  same change: it now lists every `gui/*.rs` file, and it fails if a file is added to
  `src/gui/` without being listed.

## Not run, or partial

* **`cargo fmt --all -- --check`** — not run. The project is deliberately hand-formatted, CI
  has no `fmt` gate, and every prior round records it as pre-existing noise across the
  repository.
* **Mutation testing was scoped to the semantic diff** (`main.rs`, `launch.rs`), not to the
  ~10,000 moved lines. A moved function carries the mutation coverage it had at `28dfaea`.
  That is an argument, not a measurement, and it is stated as one.
* **Host toolchain drift (the 2026-09-16 F-6 lesson):** the host stable is 1.98.1 and CI's is
  1.99.0. `rustup update stable` failed on a component conflict, so 1.99.0 was installed
  alongside it and clippy was run on 1.99.0, the gate CI actually applies.
* **The Windows packaging surface and the mobile app** were not built or tested. There is no
  Windows host, as in every prior round. The FFI public API was verified unchanged, and the
  mobile code was not touched.
* **The first mutation and Kani attempts were lost to a full `/tmp`**, a 7.6 GB tmpfs that
  holds the session scratch space. Both were rerun with scratch space on disk, and only the
  reruns are reported.

## Release impact

None of this is released or committed. A-1 and A-2 are pre-existing, and neither affects a
shipped binary's behavior. The working tree builds byte-identical binaries
(`docs/AUDIT_2026-10-10_deep.md`).

## Reproduction appendix

```bash
# Static, on CI's stable
rustup toolchain install 1.99.0 --profile minimal -c clippy
cargo +1.99.0 clippy --workspace --all-targets --all-features -- -D warnings
cargo +1.99.0 clippy -p vaultis --all-targets --no-default-features -- -D warnings
cargo audit && cargo deny check

# Public-API equality against the pre-change commit
git worktree add --detach /tmp/head-tree 28dfaea
(cd /tmp/head-tree && cargo public-api -p vaultis-core -sss) > head.txt
cargo public-api -p vaultis-core -sss > now.txt
diff <(grep -vE '^impl [A-Za-z_:]+$' head.txt | sort) <(grep -vE '^impl [A-Za-z_:]+$' now.txt | sort)

# The matrix
cargo test --workspace --all-targets
cargo test --workspace --release
cargo test -p vaultis-core -p vaultis --features vaultis/fault-injection
cargo test -p vaultis-core --no-default-features
cargo test -p vaultis --no-default-features
cargo test -p vaultis-core single_writer
cargo test -p vaultis-core --no-default-features no_op_lock

# Mutation testing on the semantic diff (scratch on DISK: /tmp is a small tmpfs here)
git diff -- crates/vaultis-desktop/src/main.rs crates/vaultis-desktop/src/launch.rs > target/audit/round.diff
TMPDIR=$PWD/target/audit/mutants-tmp cargo mutants --in-diff target/audit/round.diff -p vaultis --copy-target false --timeout 900
TMPDIR=$PWD/target/audit/mutants-tmp cargo mutants -p vaultis --file crates/vaultis-desktop/src/launch.rs -F wants_write --copy-target false   # A-1

# A-2 (fails before the fix with CONTROL FAILED; passes after)
RUSTFLAGS="-Zsanitizer=address" cargo +nightly test -p vaultis-core -Zbuild-std \
  --target x86_64-unknown-linux-gnu --test memory_residue -- --nocapture

# Fuzzing
cd fuzz && cargo +nightly fuzz build
for t in parse_header parse_frame parse_manifest scan_volume doc_paths merge_from; do
  cargo +nightly fuzz run "$t" -- -max_total_time=150 -print_final_stats=1
done
```
