# Deep Audit — 2026-07-29

A workspace-wide static + dynamic audit run immediately after **Release 0.2.0** (`ef088cc`),
covering the ~40 commits that landed since [`AUDIT_2026-07-25_round2.md`](AUDIT_2026-07-25_round2.md)
(`6f2c44d`).

**Threat model:** unchanged from [`AUDIT_2026-07-03.md`](AUDIT_2026-07-03.md) and
[`THREAT_MODEL.md`](THREAT_MODEL.md) — a standalone, OFFLINE two-password encrypted estate
vault. In scope: theft of / tampering with the on-disk vault files, a crafted vault, a hostile
merge source, a portable vault handed to the user, malicious paths/filenames/record content, a
local multi-user filesystem (permissions, symlinks, TOCTOU), and secrets lingering in memory /
on disk / in the terminal. Out of scope: network attacks, and an attacker already running as
the user with the vault unlocked in RAM.

**What this round deliberately went after that round 2 did not.** Round 2 swept the code as it
stood on 2026-07-25. Everything below is surface that *did not exist then*, which is where the
round was aimed:

* `716541d` — prefs moved into the vault root (`prefs.conf`), then `1731a95` renamed it to
  `prefs.json` and re-introduced **one** file outside any vault root: `last_root.txt`.
* `3990bdd` — the Argon2id cost became settable at creation via `VAULTIS_KDF_MCOST_MIB` /
  `VAULTIS_KDF_TCOST`.
* `59f9d10` / `b2d1e73` / `e136274` — `get_vaultis.bat` stopped compiling on the user's box and
  started **downloading a release**. That is the first thing in this project's history that
  fetches bytes off the network, so it was audited as a supply-chain surface.
* `ee99a34` — a **sample vault now ships inside the release zip**, and the read-only lock screen
  stopped drawing create affordances.
* Packaging generally: `.github/workflows/release.yml`, `scripts/release.sh`, and the
  `scripts/windows-setup-tests/` sandbox kit.

**Result:** no Critical, no High. **One Medium and two Low findings** — all three on the new
start-page/launch surface, and none in the cryptographic core, the on-disk format, the parsers,
the crash-safety machinery or the read-only gate, which all came through clean alongside 126.3 M
fuzz executions with zero crashes.

M-1 is the one that matters in practice, and it is an **emergent** defect rather than a bad line
of code: three individually reasonable decisions — shortcuts starting in the install folder, the
sample vault shipping beside the executables, and a working directory that is a folder of vaults
seeding the start page — compose into "every installed launch opens the sample vault, and the
user's real remembered root can never win." No single commit is wrong; the combination is. That
is worth stating plainly, because this round's other two findings are the familiar
guard-asymmetry shape (L-1: the write side of `last_root.txt` was hardened, the read side was
not) and its direct cause (L-2: mutation testing proved the wrapper around that file had **no
test coverage whatsoever**), whereas M-1 is the class this project has not seen before and the
one a per-file review cannot catch.

Found in the core: nothing. That is consistent with rounds 1 and 2 — there is progressively less
left there — and all three findings this round are in the desktop and packaging layers, which is
exactly where the ~40 new commits landed.

**This run is partial in one respect and the report says so plainly:** the Windows packaging
surface (the release zip's contents and SHA-256, the two executables' subsystem and DLL imports,
and the Windows Sandbox install test) **was not verified** — there is no Windows host here and no
local release artifact. See *Not run*.

## Findings

### M-1 — the shipped sample vault hijacked the start page on every installed launch (Medium, correctness)

`crates/vaultis-desktop/src/launch.rs` + `packaging/windows/make-shortcuts.ps1:90`

**What the code did.** `initial_root_and_name`'s precedence was **argument > cwd > last root >
empty**, where "cwd" meant *a working directory that is itself a folder of vaults*
(`cwd_vault_root`, qualifying iff `discover_vaults` finds a `vault.pmv` one level down). That
rule long predates this round and was harmless — until `ee99a34` shipped the sample vault.

**Why it broke.** Three independently reasonable decisions compose into a trap:

1. `make-shortcuts.ps1:90` sets `$workDir = Split-Path -Parent $Exe`, so **both** Desktop
   shortcuts launch with the working directory set to the **install folder**.
2. `ee99a34` ships the sample vault *beside the executables*, so that folder contains
   `sample-vault/vault.pmv`.
3. Therefore the install folder **qualifies as a vault root**, and cwd **outranks** `last_root`.

**The concrete result.** Every launch from either Desktop shortcut — the only way a normal
Windows user starts this program — opens the start page rooted at the install directory with
`sample-vault` in the dropdown. Worse than a cosmetic default: because cwd outranked it, the
remembered root **could never win**. `last_root.txt` was being written correctly and was
permanently shadowed, so the user's real vault root was unreachable automatically no matter how
many times they opened it.

**Severity.** Medium. There is no attacker, no data loss and no confidentiality break, so it is
not High. But it defeats the product's primary purpose on the shipped install path: an executor
following the documented route is shown a vault of *invented* estate records on every launch,
and the sample is deliberately realistic. "The heir opened the practice vault and believed it"
is a plausible outcome, and the user's real root was silently unreachable.

**Fix (user-directed).** The working-directory rule is **removed**. Precedence is now
**argument > last root > empty**; `cwd_vault_root` and `CwdRoot` are deleted. Re-ranking cwd
below `last_root` was considered and rejected: it would still pre-fill the sample on a genuine
first run, and would leave the general hazard intact — anything shipped beside the executable
could re-trigger it. Launching a specific folder is still fully supported, explicitly:
`vaultis-gui DIR`. Docs updated in `DESIGN.md`, `README.md` and the `lib.rs` prefs comment.

**Regression test.** `launch::tests::the_working_directory_never_seeds_the_start_page` — chdirs
into a directory that genuinely *is* a folder of vaults (asserting so first, so it cannot pass
vacuously) and requires both that the root comes back **empty** and that a remembered root is
**not shadowed**. Confirmed to fail when the cwd rule is reintroduced.

### L-1 — `last_root.txt` is read with an unbounded, symlink-following read (Low, robustness / defence-in-depth)

`crates/vaultis-desktop/src/launch.rs:52`

**What the code does.**

```rust
pub(crate) fn load_last_root_from(path: &Path) -> Option<String> {
    let s = std::fs::read_to_string(path).ok()?;
    ...
}
```

`std::fs::read_to_string` **follows a final-component symlink** and **allocates without any
ceiling**. This runs at GUI/TUI startup, on every bare launch, before anything else is drawn.

**What it must do.** Exactly what its sibling does. `prefs.json` — the only other small local file
this app reads — goes through `crate::read_prefs_obj` (`lib.rs:420`), which pre-checks with
`symlink_metadata` and then reads via `read_bounded_nofollow`: an `O_NOFOLLOW` open plus
`take(MAX_PREFS_SIZE + 1)`, so a symlink is refused at the open and the allocation can never
exceed the cap.

This is a **regression of an invariant the project had already established and certified**.
Round 1 fixed exactly this pattern twice (M-2 for the prefs reader, L-1 for the prefs writer), and
round 2 then verified and wrote down:

> **Raw file I/O outside the hardened helpers.** The round-1 L-1/M-2 class is fully closed: there
> is no `fs::read`, `fs::write`, or bare `File::create` left in non-test code in any of the four
> crates. Every reader is `O_NOFOLLOW` + size-capped; every writer is `O_EXCL` 0600 → rename,
> fsync'd, with the parent directory synced.

`1731a95` (2026-07-27, two days after that sentence was written) added `last_root.txt` and gave
the **write** side the hardened path — it extracted `write_atomic` precisely so the new file would
get the `O_EXCL` temp → rename discipline — but left the **read** side on a raw
`std::fs::read_to_string`. Guard asymmetry, in a single new commit, on the two halves of one file.

**The concrete input that separates them.** Reproduced by
`launch::tests::repro_last_root_read_follows_symlinks_and_has_no_size_cap` (converted to the
regression test named below):

1. **Symlink followed.** `ln -s pointed-at.txt last_root.txt` where `pointed-at.txt` holds
   `/contents/of/the/symlink/target` → `load_last_root_from` returns
   `Some("/contents/of/the/symlink/target")`. A hardened reader returns `None` (ELOOP).
2. **No size cap.** A 1 MiB file is read whole: `got.len() == 1048576`. `prefs.json` is refused
   above 64 KiB.

**Severity, and why it is Low rather than higher.** `last_root.txt` lives in the per-user OS data
directory (`~/.local/share/vaultis/` on Linux, `%APPDATA%\vaultis\data` on Windows — note that is
**roaming** AppData, so on a domain profile the OS syncs it over the network). Planting a symlink
or an oversized file there requires the user's own write privileges, so the actor who can do it can
generally already read what the symlink would point at. Nothing here touches key material, no
plaintext escapes the vault, and no vault opens for the wrong person. What is actually reachable is
a startup stall / memory blow-up (`/dev/zero`, a huge file), and an arbitrary readable file's
contents being pasted into the vault-root box. That is robustness and defence-in-depth — Low. It is
reported despite the low impact because a stated, certified invariant regressed within two days of
being certified, and because the *next* file added outside the vault root will copy whichever
pattern this one set.

**Fix.** `load_last_root_from` now reads through the same hardened helper as `prefs.json`:
`read_bounded_nofollow` (made `pub(crate)`) under a new `MAX_LAST_ROOT_SIZE` cap, with the same
`symlink_metadata` pre-check `read_prefs_obj` uses (which is what carries the guard on non-unix,
where `O_NOFOLLOW` is unavailable). Fails closed to `None` — a missing, symlinked, over-size or
non-UTF-8 file is simply "no remembered root", which is already a supported state (first run).

**Regression test.**
`launch::tests::last_root_read_refuses_a_symlink_and_caps_the_size`, which asserts both halves
(symlink → `None`; over-cap file → `None`) and keeps the existing round-trip test passing so the
feature itself is still covered.

### L-2 — the `last_root.txt` OS wrapper had no test coverage at all (Low, test coverage)

`crates/vaultis-desktop/src/launch.rs:43-85`

**What mutation testing showed.** `cargo mutants`, scoped to `launch.rs`, reported four survivors
— and all four were in the same two functions:

```
replace last_root_file  -> Option<PathBuf> with None
replace last_root_file  -> Option<PathBuf> with Some(Default::default())
replace load_last_root  -> Option<String>  with Some(String::new())
replace load_last_root  -> Option<String>  with Some("xyzzy".into())
```

**These are not equivalent mutants.** Each visibly changes what the program does on launch:
`load_last_root -> Some("xyzzy")` makes every bare launch open the start page pointed at a
nonexistent root, and `last_root_file -> None` makes the remembered root silently never persist.
The entire 671-test suite stayed green for all four.

**Why they survived.** Both functions begin `if cfg!(test) { return None }` / `{ return }`. That
guard is deliberate and correct — this is the one file at a single *fixed* OS path shared by every
test and the real app, so a unit-test run must neither read the developer's real `last_root.txt`
nor clobber it. The logic was split into `load_last_root_from` / `save_last_root_to`, which *are*
tested. But the wrapper that remained — the `cfg!(test)` guard itself, the `ProjectDirs` path
resolution in `last_root_file`, and the delegation — was left reachable by **no test at all**. That
is precisely the region where a "my remembered vault root is being lost" bug would live, and
nothing would have caught it.

**Verified by hand first.** Before writing anything, the real path was exercised end-to-end with
`XDG_DATA_HOME` redirected at a scratch directory (so `cfg!(test)` is false and the developer's
real file is untouched): first load → `None`; save `/home/somebody/my vaults` → load returns it
verbatim, spaces included; save again → replaces rather than appends; the file lands at
`<data dir>/vaultis/last_root.txt` as a regular file, mode 0600. **The feature is not broken** —
it is merely unverified, which is a different problem with the same fix.

**Fix.** A new **integration** test, `crates/vaultis-desktop/tests/last_root_os_file.rs`. An
integration test compiles `vaultis` as an ordinary dependency, so `cfg!(test)` is **false** inside
the library and the real path runs; `XDG_DATA_HOME` redirects `ProjectDirs` at a scratch dir so
nothing touches the developer's data directory. Linux-only, because that redirection is
XDG-specific (macOS resolves to `~/Library`, Windows to a known folder).

**Regression test.** `last_root_round_trips_through_the_real_os_file`. Confirmed to **kill** the
survivors rather than merely pass: reintroducing `load_last_root -> Some("xyzzy")` fails it on
*"first run has no remembered root"*, and `last_root_file -> None` fails it on *"the saved root must
come back exactly"*. It also asserts the L-1 symlink refusal on the **real** OS path, not just on
the `_from` helper.

## Leads chased and refuted (so the next round need not re-chase them)

* **The KDF cost env override** (`VAULTIS_KDF_MCOST_MIB` / `VAULTIS_KDF_TCOST`,
  `lib.rs:187`). Sound. The MiB→KiB conversion is `saturating_mul` so a silly value cannot wrap
  into a *weak* cost; the result is gated by `KdfParams::validate()`, which is the **same** gate
  `Header::parse` uses on read, so this cannot write a vault the reader would refuse; an
  unparseable value falls back per-field with a warning; and landing exactly on the default is
  correctly reported as "not non-default" rather than announced. All three real create sites route
  through it (`gui.rs:1830`, `ui.rs:1178`, `main.rs:911` → `import_tree`). The weak `fast()` params
  at `gui.rs:6832` are inside `#[cfg(test)]`, so no shipped path creates a weak-KDF vault.
* **The shipped sample vault's published passwords.** `sample1`/`sample2` are in the source, the
  Help manual and the release workflow, and in Edit mode the sample vault opens **writable** — so
  a user could put real data behind publicly-known passwords. Not a defect: it is disclosed at both
  points of contact, by the button's hover text ("a throwaway practice vault full of invented
  data") and by an explicit `Block::Warn` in Help ("Never put real information into the sample
  vault, and never reuse sample1 or sample2 as passwords on a vault of your own"). Recorded here
  because it *looks* like a finding and will be re-noticed.
* **Read-only really being read-only.** Every mutating public method on `OpenVault` carries the
  `if self.read_only { return Err(VaultError::ReadOnly) }` guard — `save`, `set_redundancy`,
  `change_password`, `compact`, `set_volume_max_size`, `add_document`, `remove_document`,
  `apply_merge_from`, `sync_types_from_records`, and every `remove_*`. The three `add_*_type`
  entry points delegate to `mutate_categories`, which guards. The open-time refresh save is itself
  gated (`if !read_only` at `vault.rs:547`). No path into a write escapes the gate.
* **The clipboard.** There are exactly **two** `.password(...)` renderings in the whole GUI and
  both are inside `secret_text_edit`, so no secret field bypasses the hardened path. egui's
  built-in Ctrl+C/Ctrl+X/context-menu copy is intercepted at the focused field: the staged
  `OutputCommand::CopyText` is `mem::take`n (deliberately **not** cloned, which would strand an
  un-zeroized cleartext copy in freed heap), the commands are dropped so eframe's plain `set_text`
  never runs, and the secret is re-routed through the armed 15 s auto-clear + on-exit wipe.
* **`detail_is_secret` is case-sensitive.** It masks history values by
  `name.trim_end().ends_with("password")`, which would miss a capitalised `Password:`. Not
  reachable: every field name is a lowercase literal passed to `track(...)`, all five secret fields
  end in `password`, and there is no capitalised `track` name anywhere in `records.rs`. The rule is
  suffix-based rather than an enumerated list, so a future `*password` field is covered
  automatically.
* **A TOCTOU in the single-writer lock.** There isn't one. `WriteLock::acquire` performs a single
  `O_NOFOLLOW`, no-truncate open and then `flock`s **that same file description** — there is no
  stat-then-open window, a symlinked lock path is refused as `Locked`, and the lock is held for the
  lifetime of the `File`.
* **`volume_max_size` / `redundancy` write-vs-read bound drift** (the L-2 shape from round 1).
  Both are clamped on the untrusted `import_tree` path (`vault.rs:778-779`) and on the setter; a
  plain open trusts a value that is authenticated by the AEAD *and* was already clamped by whatever
  wrote it. No value the write side can produce is refused by the read side.
* **Raw file I/O outside the hardened helpers, re-swept across all four crates.** `launch.rs:53`
  (the finding) is the **only** unhardened reader in non-test code. The other apparent hits are
  benign: `main.rs:845/856` are `read_dir` (directory listing, not an unbounded file read), and
  `main.rs:1289+` are inside `crashop`, which is `#[cfg(feature = "fault-injection")]` test harness
  and is not compiled into a shipped binary.
* **`get_vaultis.bat`'s download path.** It satisfies both properties this project requires: it
  **refuses an asset with no `.sha256`** (fails closed with an explicit message rather than
  installing something unverifiable) and **refuses a hash mismatch**. It downloads into a fresh
  GUID-named temp directory rather than a predictable path, and cleans it up in a `finally`. It is
  also honest in-comment that the checksum proves integrity, not authorship, since the hash travels
  from the same host as the zip — Authenticode signing is what would bind the bytes to a publisher,
  and it says so.
* **PowerShell encoding in the packaging surface.** PSScriptAnalyzer flags
  `PSUseBOMForUnicodeEncodedFile` on `packaging/windows/make-shortcuts.ps1`, which is a real hazard
  in principle — `get_vaultis.bat` invokes **Windows PowerShell 5.1** (the fixed System32 path),
  which decodes a BOM-less file as the ANSI codepage rather than UTF-8. Consequence here is nil: the
  file's only non-ASCII byte sequence is an em-dash inside a `#` comment (line 111), and UTF-8
  continuation bytes are never `0x0A`, so a mis-decode cannot break the comment out of its line.
  `get_vaultis.bat` itself is pure ASCII, and its embedded section is read by
  `[IO.File]::ReadAllText`, which is UTF-8 by default — so neither file has a reachable encoding
  bug.
* **Duplicate source ids in a merge.** Handled symmetrically on **both** sides: `collection_changes`
  de-duplicates with a `HashSet` keeping the first occurrence, and `merge_records` independently
  applies each accepted id at most once. A crafted source cannot double-list a record in the preview
  or insert-then-replace it during apply.
* **AAD binding.** Re-derived rather than assumed: the vault header is sealed with the **entire**
  header as associated data (`vault.rs:2812`, `crypto::encrypt_with_nonce`), and the manifest and
  volume bind **both** the vault id and the partition index (`manifest_aad` / `volume_aad`), with
  tests asserting that a wrong vault id and a wrong partition each fail to decrypt.
* **A `prop_redundancy_ring_well_formed` failure — environmental, not a bug.** Mid-round, this
  proptest failed during a full `--workspace` run. It was chased to ground rather than retried away.
  The panic is `Io(Os { code: 122, kind: QuotaExceeded })` from `OpenVault::create(...).unwrap()` at
  `vault.rs:6893` — the *test harness* running out of space, not the redundancy ring misbehaving.
  Cause: **`/tmp` on this machine is a 7.6 GiB tmpfs**, `cargo-mutants` had been left building a
  **6.1 GiB scratch tree inside it**, and the vault tests create their vaults in `/tmp` too. Two
  independent confirmations: the case shrank to `depth = 1, saves = 1` (the *simplest* possible
  input — the signature of resource exhaustion, since a genuine logic bug shrinks to a specific
  interesting combination), and that exact case passed **12/12** when re-run in isolation. Proptest
  appended a seed for it; that seed was **reverted**, because pinning an out-of-disk failure would
  make every future run re-execute a case that tests nothing. Lesson for the next round: point
  `TMPDIR` at real disk before running `cargo-mutants` here, or it competes with the very tests it
  is running.
* **The fuzz harnesses are not no-ops.** Checked before quoting their execution counts: `doc_paths`
  asserts charset, length bounds, edge-dot/dash, absence of separators/controls, prefix preservation
  and traversal-freedom; `merge_from` builds an attacker-shaped source vault (duplicate ids,
  negative and `i64::MAX` timestamps, a document-bearing record) and asserts the destination still
  opens afterwards. The exec counts below therefore represent real coverage.

## Not run

Stated explicitly rather than implied, because this was a post-release audit and these are exactly
the checks a release warrants:

* **The release zip's contents, layout and SHA-256; both executables' subsystem (console vs GUI);
  and their DLL imports.** Not verified — no Windows host, and no release artifact present locally.
  The *workflow* that produces them was read (`.github/workflows/release.yml` stages a flat folder,
  asserts an explicit file manifest including `sample-vault/vault.pmv`, removes a stale
  `vaultis.lock` from the seeded sample, and publishes `<zip>` plus `<zip>.sha256` in
  `sha256sum` format) but reading a workflow is not verifying an artifact.
* **The Windows Sandbox kit** (`scripts/windows-setup-tests/`) — requires Windows Sandbox. What was
  done instead: all four PowerShell files (`get_vaultis.bat`'s embedded section extracted exactly as
  the batch header extracts it, plus `make-shortcuts.ps1`, `make-sandbox-configs.ps1`,
  `prep-and-run.ps1`) were **parsed** with PowerShell 7.6.4 and linted with PSScriptAnalyzer. All
  parse cleanly. CI never syntax-checks any of them, so this closed a real gap — a syntax error in
  the installer would break the first thing every new user runs.
* **`cargo fmt --all -- --check` fails** (28 files, 1509 hunks). This is **not** a finding: CI states
  the policy in its own header — *"The project is deliberately hand-formatted, so there is NO
  `cargo fmt` check."* Recorded so a future round does not mistake it for a regression.
* **Mutation testing was scoped, not exhaustive.** See below.

## Reproduction appendix

```bash
# Phase 1 — static
```
