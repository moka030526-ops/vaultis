# Audit — 2026-09-16

A change-scoped static + dynamic audit of the **unreleased 0.3.0** work (`3f712b7..1337f5b`),
run on top of the full regression matrix, **before** the release tag is pushed. The three
commits under review:

* `854cac0` — a new **Zakat** record collection and tab (four columns: Ramadan Year, Amount
  Due, Amount Paid, Remaining), copy buttons on the Real Estate portal URLs/usernames, and
  bordered View-row toggles. Touches the core record model, the cross-vault merge, the CSV
  export, both desktop front-ends, the FFI and the mobile viewer.
* `e6d0b5a` — storage test hardening for the previous round's A-6 (a `CountingVolume` that
  makes the resync cost controls observable).
* `1337f5b` — Release 0.3.0: the version bump, changelog, and `fuzz/Cargo.lock`.

**Threat model:** unchanged from [`THREAT_MODEL.md`](THREAT_MODEL.md). In scope: theft of or
tampering with the on-disk vault files, a crafted vault, a hostile merge source, malicious
paths/filenames/record content, a local multi-user filesystem, and secrets lingering in memory
or on disk. Out of scope: network attacks, and an attacker already running as the user with the
vault unlocked in RAM.

**What this round deliberately went after that the last one did not.** The 2026-08-03 round
audited a change to the untrusted-input *parser*. This round is a different shape: 0.3.0 adds
the **first new record collection since 0.2.0**, and it does so with a **tab that saves every
row at once** rather than one record at a time — the first in the program. Every per-save side
effect that was previously scoped to the single record a user had open is now multiplied across
a whole collection. The round was aimed at five questions:

1. Does the new collection reach every whole-vault path (merge, history compaction, bulk trim,
   CSV, backup, the FFI) or is it silently omitted from one?
2. Does saving a *table* rather than a *record* break any invariant that assumed the latter?
3. Is the derived `Remaining` column consistent across the three front-ends and the CSV, or does
   one of them present a number the others do not?
4. Is the read-only gate intact on a tab that renders editable widgets in read-only mode?
5. Did the release preparation itself leave the project in a releasable state?

**Result: one High, six Low.** The High (F-1) is a defect in code written earlier in this same
session: saving the Zakat tab stamps `updated_at` on **every** row, including untouched ones, and
because `updated_at` is the cross-vault merge's recency key, a later merge **silently discards a
genuine edit made on another machine** — with the merge preview reporting nothing at all. It is
answer to question 2, and it is exactly the class the question was asked about.

Question 5 produced four of the Lows and is the reason this round was run before the tag rather
than after: **CI is red on `main` right now**, on three separate jobs, and none of the three were
caused by the feature work. A release cut today would have shipped from a red tree.

The cryptographic core, the key derivation, the on-disk format, the record parsers, the
single-writer lock and the read-only gate on the record APIs all came through clean, as in the
four rounds before this one.

Worth stating plainly: the feature work was audited by the same session that wrote it, and the
most serious finding is in that work. That is the second round running where fresh code is where
the findings were.

## Findings

### F-1 — saving the Zakat tab falsely claims recency on every row, silently losing a real edit on merge (High, data loss)

`crates/vaultis-desktop/src/gui.rs` (`GuiApp::save_zakat`)

**What the code does.** The Zakat tab is a table, so its Save writes the whole ledger:

```rust
let rows = self.edit_zakat.clone();
if let Some(ov) = self.vault.as_mut() {
    for r in rows {
        records::upsert(&mut ov.vault.zakat, r);   // every row, changed or not
    }
}
```

`records::upsert` opens with `rec.set_updated_at(now)` **unconditionally** (`records.rs:1160`).
So one Save re-stamps every row in the collection, including rows the user never touched. The
content is unchanged and `diff` produces no history entry — only the timestamp moves, which is
what makes it invisible.

**What it must do.** Only write rows that actually changed. `updated_at` is not decoration: it is
the cross-vault merge's **recency key**, and the codebase says so in two places. `merge.rs:12`
defines it as such, `merge.rs:208` implements the comparison as `s.updated_at() > c.updated_at()`
(strictly newer wins), and `merge.rs:225` carries an explicit warning that the merge apply path
deliberately avoids `upsert` *because* "upsert stamps `updated_at = now`". `records::trim_all`
— the other bulk writer in the program — already does the right thing, upserting only records
whose `trim_fields()` reported a change, and its doc comment says so. `save_zakat` is the single
place in the program that violates the rule.

**The concrete input that separates them.** Two machines sharing a vault (a backup, or a second
device — the workflow `plan_merge_from` exists for):

1. Both have zakat row *1445*, `amount_paid = "1000"`, `updated_at = T`.
2. On machine **B**, the user records the payment: `amount_paid = "3000"`, `updated_at = T+100`.
   A real edit, genuinely newer.
3. On machine **A**, the user edits a *different* year (1446) and clicks Save. A's untouched 1445
   row is re-stamped to `T+900`.
4. Merge B → A.

Observed:

```
A 1445 content : "1000"
A 1445 ts      : T+900   (B's genuine edit is at T+100)
plan records   : 0
plan skipped   : 0
merged add/upd : 0/0
A 1445 AFTER   : "1000"   (B had "3000")
REAL EDIT LOST : true
```

The plan is **empty** — not "skipped", empty — so the preview the user authorizes shows nothing
about this row at all. They see "nothing to update", conclude the vaults agree, and B's payment
record is gone the moment B is discarded.

**Severity: High, and why.** It is silent data loss in an estate vault, triggered by ordinary use
of the feature: every Save on the tab re-stamps the whole collection, so the window is not an edge
case but the default state after any visit to the tab. Nothing warns, and the preview — the
control the merge design leans on for authorization — is empty rather than merely wrong. It is not
Critical: no plaintext escapes, no vault opens for the wrong person, and the loss is confined to
the `zakat` collection (every other tab upserts only the one record the user had open, which is a
defensible stamp). It is mitigated by the fact that **this code is unreleased** — the finding is
against a tag that has not been pushed, which is the reason for running the audit before it.

**Fix applied.** Upsert only the rows whose content differs from the saved copy, comparing by id
against `ov.vault.zakat` and ignoring the bookkeeping fields `upsert` maintains itself
(`updated_at`/`history`) — the same rule `trim_all` follows. Verified both directions: with the
filter reverted, `zakat_save_does_not_restamp_untouched_rows` fails on
`left: …198 / right: …698` and `zakat_save_cannot_mask_a_newer_edit_from_another_vault` fails on
`the preview must show the incoming edit … left: 0, right: 1`; with it in place both pass.

**Regression tests.** `zakat_save_does_not_restamp_untouched_rows` (an untouched row keeps its
`updated_at` across a Save that changes a different row, while the edited row is correctly stamped)
and `zakat_save_cannot_mask_a_newer_edit_from_another_vault` (the four-step two-vault reproduction
above, asserting the plan is non-empty **and** B's edit lands).

### F-2 — the Zakat table is unreadable to assistive tech and uncopyable in a read-only session (Low, accessibility/robustness)

`crates/vaultis-desktop/src/gui.rs` (`GuiApp::tab_zakat`)

**What the code does.** The table's cells are `TextEdit`s gated with `.interactive(writable)`.
Writes *are* correctly blocked — in a read-only session the Save, ➕ New Year and 🗑 buttons all
render zero times, and the values cannot be edited. But `interactive(false)` also removes the
widget from the accessibility tree entirely.

**What it must do.** Stay selectable and readable. `field_singleline` — the helper every other tab
uses — carries a comment explaining precisely this choice:

> egui edits require a *mutable* `TextBuffer` while selection only needs an interactive widget — so
> binding a `&str` (an immutable `TextBuffer`) gives a read-only field whose text the user can
> still highlight and Ctrl+C, exactly what read-only mode wants (vs. `add_enabled(false)`, which
> greys it out and blocks selection entirely).

`tab_zakat` introduced a third mechanism with the same defect the project had already rejected
`add_enabled(false)` for.

**The concrete input that separates them.** One read-only session, both tabs, counting accessibility
nodes carrying each value:

```
Zakat  "1446" nodes : 0      "4000" nodes : 0      "1000" nodes : 0
Taxes  "2024" nodes : 1      "Joint" nodes : 1
```

**Severity: Low, and why.** No data loss, no secret exposure, and the read-only *write* gate is
intact — this is not a bypass. It is filed because read-only is not a corner case here: it is the
desktop's default mode and the mobile viewer's only mode, so the affected user is the heir reading
the vault, and the affected capability is selecting, copying, or having a screen reader announce
the amounts. For a program whose users are explicitly expected to include executors who did not
set the vault up, that is worth a finding rather than a note.

**Fix.** Render the cells through the same writable/read-only split the rest of the program uses,
so a read-only cell is an immutable-but-selectable field rather than an inert one.

**Fix applied.** A `zakat_cell` helper renders each cell as a `TextEdit` when writable and through
`read_only_value` — the same immutable-but-selectable field the rest of the program uses — when not.

**Regression test.** `zakat_values_stay_selectable_in_a_read_only_session`, asserting one
accessibility node per value in a read-only session, *and* that the three write affordances (Save,
➕ New Year, 🗑) remain absent — so the fix cannot be "made accessible" by accidentally re-enabling
editing.

### F-3 — a non-finite `Remaining` reaches the CSV and the phone as the literal text `inf` (Low, robustness)

`crates/vaultis-core/src/csv.rs` (`zakat_csv`), `crates/vaultis-ffi/src/lib.rs` (`map_zakat`)

**What the code does.** `ZakatEntry::remaining` subtracts two parsed amounts. `parse_approx_value`
rejects a non-finite *field*, so each side is finite — but their difference need not be. The GUI
renders the result through `crate::fmt_money`, which guards this explicitly (`"$—"` for a non-finite
value, with a test whose comment calls it "a fabricated figure presented as a real one in a
financial view"). The CSV and the FFI both format it raw:

```rust
r.remaining().map_or_else(String::new, |v| format!("{v}"))
```

**What it must do.** Apply the same guard the GUI does. The FFI DTO's own contract says `remaining`
is "Due − paid as plain digits (e.g. `"1500"`), or `""` when it cannot be worked out" — `inf` is
neither.

**The concrete input that separates them.** Two individually-finite amounts:

```
amount_due = "1.7e308", amount_paid = "-1.7e308"
remaining()  = Some(inf)
CSV cell     = "inf"
```

The totals row is also affected: a 309-digit integer reaches the CSV for the same input.

**Severity: Low, and why.** It needs absurd amounts — reachable by a typo or from a crafted merge
source, but not by any realistic ledger — and nothing is lost or corrupted. It is filed because it
is this project's signature **guard asymmetry**: three renderers of one derived value, one guarded
and two not, with the guarded one carrying a test that explains why the guard exists.

**Fix.** Route both through the same non-finite check, emitting the empty cell the DTO already
documents for "cannot be worked out".

**Fix applied.** The guard went into `ZakatEntry::remaining` itself rather than into each boundary,
so the table, the totals row, the CSV and the phone all report "cannot be worked out" identically
and cannot drift apart again. `fmt_money`'s own non-finite guard is left in place as defence in
depth — the *totals* sum many rows and can overflow independently of any single one.

**Regression tests.** `zakat_remaining_is_none_when_not_finite` (both overflow directions, plus a
large-but-representable difference that must still be reported) and
`zakat_csv_never_emits_a_non_finite_remaining` (asserting the cell is empty, not `inf`).

### F-4 — a dependency vulnerability is unfixed and the supply-chain gate is red (Low, supply chain)

`Cargo.lock` (`webbrowser` 1.2.1)

**What the code does.** `cargo audit` reports **RUSTSEC-2026-0257** — *"Unix `BROWSER` handling
allows browser argument injection"*, dated 2026-07-29, fixed in 1.2.2. It is a **vulnerability**,
not an allowed warning, so `cargo audit` exits non-zero and `cargo deny check` reports
`advisories FAILED`. CI gates on both (`ci.yml:57-70`), so this job fails on every push.

**What it must do.** Pass, or carry a written justification in `.cargo/audit.toml` — that file's own
header states the policy.

**Reachability.** Not reachable in vaultis. `webbrowser` arrives via
`eframe → egui-winit`, and is only invoked when egui emits an `OpenUrl` output command. The program
contains **no `Hyperlink`, no `ui.link`, no `OpenUrl`, and no `BROWSER` use** — verified by grep
across the workspace; the single `output_mut` call site is the password-copy hardening. The
vulnerable code is linked but never called.

**Severity: Low, and why.** Unreachable, so no user is exposed. It is filed at Low rather than
dismissed because it is nonetheless a **release blocker**: the supply-chain gate is one of the
checks the project relies on, and shipping with it red both hides the next real advisory and breaks
the "every surfaced advisory carries a justification" discipline.

**Fix applied.** `cargo update -p webbrowser` took 1.2.1 → 1.2.4, in-range, no manifest change.
`cargo audit` now reports no vulnerabilities and `cargo deny check` reports
`advisories ok, bans ok, licenses ok, sources ok`.

### F-5 — an unsoundness advisory is untriaged again (Low, supply chain / process)

`.cargo/audit.toml` (`lru` 0.18.0)

**What the code does.** `cargo audit` reports **RUSTSEC-2026-0253** (`lru` 0.18.0, potential
use-after-free from lack of panic safety in `LruCache::pop()`) as an allowed warning with no
`audit.toml` entry and no justification. It reaches the build through
`ratatui → ratatui-core`, i.e. the TUI front-end.

**What it must do.** Carry a justification or be fixed. This is the **exact shape of the previous
round's A-4**, which was filed on the same principle four rounds ago: *"the project's discipline is
that every surfaced advisory carries a written justification, and an untriaged one erodes that."*

**Severity: Low, and why.** An unsoundness requiring a panic inside `LruCache::pop` during
ratatui's internal caching; no demonstrated reachability. Filed for the recurrence, not the bug —
A-4's fix was to triage that one advisory, not to prevent the next one from sitting untriaged.

**Fix applied.** `cargo update -p lru` took 0.18.0 → 0.18.4, dropping the warning without an ignore
entry — the same resolution A-4 took. `.cargo/audit.toml` is unchanged and still carries only the
three justified entries.

### F-6 — the clippy gate is toolchain-dependent, and a local run reports a false green (Low, process)

`crates/vaultis-desktop/src/gui_tests.rs:611`, `.github/workflows/ci.yml`

**What the code does.** CI runs `dtolnay/rust-toolchain@stable` with
`cargo clippy --all-targets --all-features -- -D warnings`. Rust **1.98.0** added
`clippy::chunks_exact_to_as_chunks`, which fires on a line that has been in the tree since
`afacd53`:

```
error: using `chunks_exact` with a constant chunk size
   --> crates/vaultis-desktop/src/gui_tests.rs:611:23
```

CI was green on `3f712b7` (2026-08-03) and is red on `854cac0` (2026-09-16); nothing in between
touched that line. The gate moved, not the code.

**What it must do.** Be reproducible locally. This round's Phase 1 initially reported clippy
**clean** — because the audit host's stable was 1.96.0 (2026-05-25) while CI's was 1.98.1
(2026-09-01). The local gate and the CI gate were two different gates, and only the weaker one was
run. The finding was only reached by reading CI's logs, not by running the documented command.

**Severity: Low, and why.** A lint on test code, with no runtime effect. Filed because the failure
mode is an **auditing** one: `cargo clippy -D warnings` is step one of this skill's Phase 1, and it
silently under-reports whenever the host toolchain lags CI. That is coverage claimed but not
obtained, which the house rules single out as the thing not to do.

**Fix applied.** A targeted `#[allow(clippy::chunks_exact_to_as_chunks)]` at the call site, with a
comment explaining the choice. The lint's suggested rewrite (`as_chunks::<4>()`) was **rejected**:
`as_chunks` stabilised in the same release that added the lint, so taking the suggestion would make
the test require the newest stable to compile — widening exactly the local-versus-CI toolchain gap
this finding is about. The audit host was updated to 1.98.1 and the reproduction appendix now opens
with `rustup update stable`, so Phase 1's clippy step matches the gate that actually blocks.

### F-7 — the only cross-language check on the mobile app has been failing, so this release's Kotlin change is unverified (Low, process)

`.github/workflows/ci.yml` (`android apk build`)

**What the code does.** The FFI surface-lock test states plainly that "the android APK job is the
cross-language backstop" — it is what compiles `App.kt` against the generated UniFFI bindings, and
the FFI's exhaustive `when` over `RecordKind` is designed to fail that build if a new record kind
is unhandled. The job now fails during setup:

```
Warning: Failed to find package 'tools'
Error: The process '…/cmdline-tools/16.0/bin/sdkmanager' failed with exit code 1
```

`android-actions/setup-android@v3` aborts before Gradle runs, so **no Kotlin is compiled**.

**What it must do.** Compile. `854cac0` adds `RecordKind.ZAKAT` to the FFI and a matching branch to
`App.kt`'s exhaustive `when`; the backstop designed to verify exactly that never executed. The job
passed on `3f712b7`, so this is environment drift (the Android SDK dropped the obsolete `tools`
package), not a consequence of the change.

**Severity: Low, and why.** No defect is demonstrated in the Kotlin — the change is small and the
`when` arm is present. It is filed at Low, not dismissed, because the *verification* is absent: the
mobile viewer is the one front-end this round could not build or test, and its build gate has been
red long enough that nobody noticed. Same principle as the previous round's A-3: a control that does
not run reads as coverage on the next round.

**Fix: NOT APPLIED.** Left for a separate change. It is a CI-environment fix that cannot be
verified from here — the failure is inside `android-actions/setup-android@v3`'s SDK resolution, so
the only way to confirm a fix is to push it and watch the runner. Doing that inside an audit commit
would mean shipping an unverified change to the one job that is supposed to be the verifier. Filed
with the diagnosis; the fix belongs in its own commit with its own CI run.

## Leads chased and refuted

* **Is the new collection omitted from any whole-vault path?** No. Verified by reading and by
  probe: `compact_history`, `history_stats` and `trim_all_records` all include `zakat`; the merge
  plans and applies it (a probe confirmed a row crossing vaults with its id, content and history
  intact); the CSV dispatch maps it; `backup`/`copy_dir` are collection-agnostic; and the FFI's
  deliberately-exhaustive `Vault` destructure in `lib_tests.rs` forced the question and was
  answered with a `RecordKind`, a DTO, a getter and a mobile tab. `referenced_doc_ids` correctly
  does *not* mention it — zakat rows carry no documents.

* **Does a zakat row survive save → reopen?** Yes — probed directly (row count, content and the
  derived `remaining` all intact after a close and re-open). The on-disk format stays v4 because
  the field is `#[serde(default)]`. Note the *absence of a test* for this: `format_compat.rs` has
  no zakat round-trip, so the guarantee is currently unasserted (see Coverage gaps).

* **Does the bulk "Trim all fields" action have F-1's defect too?** No — and this is what confirmed
  F-1 is a deviation rather than a house pattern. `records::trim_all` collects only the records
  whose `trim_fields()` returned `true` and upserts those, so an unchanged record is never
  re-stamped. Its doc comment states the behaviour explicitly.

* **Can history compaction be undone by a stale Zakat buffer?** The tab renders from a whole-table
  buffer rather than re-reading the vault each frame, so a wholesale change to `vault.zakat` behind
  its back would be written straight back by the next Save. Refuted on reachability: compaction is
  reachable only from the CLI (`main.rs`), which takes the single-writer lock, so it cannot run
  while a writable GUI session holds the vault; a read-only GUI session cannot Save. The two GUI
  actions that *do* mutate records wholesale — the bulk trim and merge-apply — both re-sync the
  buffer (added in `854cac0`), and they are the complete set.

* **Does the new `0` key in the TUI shadow anything, or fire while typing a search query?** No.
  `handle_browse_key` intercepts `search_active` and returns before reaching any command key, so
  `0` in the search box appends to the query. In browse mode `0` was previously unbound.

* **Is record text sanitized before the Zakat table renders it?** No — and neither is any other
  tab's. `display_safe` is applied at the CSV boundary and to category names on the merge path, not
  to record field values in the GUI. A crafted merge source can put bidi controls in
  `ramadan_year`, exactly as it can in a tax year or an account title. Pre-existing, unchanged by
  this round, and not filed as new.

* **Can `zakat_csv` be used for CSV formula injection?** No. Every cell goes through `esc`, which
  runs `display_safe` and prefixes `'` to a cell starting `=`, `+`, `-` or `@`. This matters for
  the derived column specifically: a negative remainder renders as `-2500`, which the guard catches.

* **Do the new Real Estate copy buttons ever put a secret on the clipboard without the auto-clear?**
  No. They are wired to `copy_plain`, which is reached only from the URL and username fields; the
  password keeps `copy_to_clipboard` and its 15 s timer. Cancelling a pending clear on a non-secret
  copy is correct and deliberate — the fresh non-secret has already overwritten the clipboard, so
  there is no longer a password on it to wipe.

* **Does `delete_zakat_row` report success when there is no vault?** It would — the row leaves the
  buffer, the status says "Deleted." and nothing is persisted. Not filed: `tab_zakat` is only
  rendered from the main screen, whose invariant ("vault is open on the main screen") is asserted
  by `vault_ref`'s `expect` and relied on by every other tab in the file.

* **Are the zakat amount buffers pre-sized against reallocation stranding cleartext?** No, and they
  should not be. `presize_secret` is applied to passwords only (account, and the four portal
  passwords); the comparable financial field `AssetLiability::approx_value` is not pre-sized either.
  Consistent with the house rule.

## Coverage gaps (not findings, but unasserted guarantees)

Each of these is a guarantee this round verified **by probe** and found holding, which no test
pins. They are recorded rather than fixed because a coverage gap is not a defect — but the next
round should not have to re-derive them by hand.

* `format_compat.rs` has no zakat round-trip, so "the new collection survives save/reopen, and a
  vault written before it still loads" rests on `#[serde(default)]` alone.
* No test asserts a zakat row survives a cross-vault merge with its id, content and history intact.
* `gui_help_tests.rs::every_documented_feature_is_findable_by_search` carries an explicit list of
  features that must be reachable from the manual's search. The new Zakat article is not on it, so
  the manual's coverage of the new tab is unasserted.
* Mutation coverage of the new code is 7/221 — see *Not run, or partial*. The three fixes in this
  round each ship with a test confirmed to fail on the pre-fix code, which is stronger evidence for
  those three specific behaviours than a mutant would have been, but it says nothing about the rest.

  suite costs ~50 s per invocation) well beyond that; and the round had by then already found a
  High that needed fixing, so mutating code about to be rewritten was not worth the wall time.
  **This round therefore does NOT make the "no surviving mutant" claim** that earlier rounds made
  — 7/221 is a sample, not coverage. Notably the untested set includes every mutant inside
  `save_zakat` and `tab_zakat`, the two functions F-1 and F-2 live in. Re-run with headroom:
  `cargo mutants --in-diff /tmp/round.diff -p vaultis-core --timeout 300` and again with
  `-p vaultis`.
* **`cargo llvm-cov`** was not run. This round touches the record model, the CSV boundary and the
  merge, not the crypto or storage core, and the host was disk-constrained throughout.
* **The Windows packaging surface was not executed.** No Windows host is available — the same
  limitation as the previous round. What *was* checked, by reading: `get_vaultis.bat` refuses an
  asset published without a `.sha256` beside it, downloads into a freshly-generated random temp
  directory (so a predictable path cannot be pre-created and swapped), verifies before extracting,
  and refuses on mismatch; and `release.yml` does publish `<zip>.sha256` in the `sha256sum` format
  the installer parses, so the two halves agree. **Not** checked: the zip's actual contents and
  layout, the two binaries' subsystems (console vs GUI) and DLL imports, the real install through
  the Windows Sandbox kit in `scripts/windows-setup-tests/`, and the published SHA-256 of an
  actual release artifact.
* **The mobile app was neither built nor tested** — see F-7. The Kotlin change in this release has
  no verification of any kind.
* **Kani proofs, ASan/LSan/TSan, the memory-residue observation and the reproducible-build check**
  were not run — they are the `deep-audit` scope, last exercised on 2026-07-29.
* **CodeQL** remains red for the pre-existing reason recorded on 2026-08-03 (GitHub's default setup
  cannot autobuild the `mobile/` Kotlin app). Unchanged by this round.

## Release impact

**Nothing here reached released code.** `v0.3.0` was not tagged; `scripts/release.sh` was
deliberately held until this audit completed. That is the whole value of the round's timing: F-1 is
silent data loss that would otherwise have shipped in the first release to carry a new record
collection into people's vaults, and F-4/F-6/F-7 meant the tree was red on three CI jobs that a
release cut that morning would simply have ignored — `release.sh` checks the tag, the crate version,
the working tree and the changelog, but **not CI**.

**Six of the seven findings are fixed in this round.** F-1, F-2 and F-3 are fixed with regression
tests that were each confirmed to fail on the pre-fix code; F-4 and F-5 are fixed by dependency
updates that take `cargo audit` and `cargo deny check` back to clean; F-6 is fixed at the call site.

**F-7 is deliberately left open** — see its entry. It is a CI-environment fix whose only possible
verification is a push and a runner, so it belongs in its own commit rather than inside an audit
commit. The practical consequence stands and should be weighed before tagging: **the mobile Kotlin
change in 0.3.0 has never been compiled**, here or in CI.

**Recommended sequence:** land these fixes, confirm CI goes green on all jobs except `android apk
build`, fix F-7 separately and confirm that job too, then re-run `scripts/release.sh`. The version
bump, changelog and `fuzz/Cargo.lock` in `1337f5b` remain valid — only the tag was withheld.
