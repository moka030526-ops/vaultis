# Audit — 2026-08-03

A change-scoped static + dynamic audit of **release 0.2.7** (`92120ee..2a8c91c`), run on
top of the full regression matrix. The four commits under review:

* `402c23a` — the GUI's unsaved-changes indicator: a successful save now re-reads the
  written record back into the form buffer, at fourteen upsert-then-persist sites.
* `fb0873a` — storage: a spare copy of each partition manifest (`manifest.<N>.mirror`)
  under the existing redundancy setting, a volume scan that resynchronises past a
  damaged frame instead of stopping at it, and a stale-spare tail merge.
* `7622523` — the in-app manual: backups moved into Getting started, plus a new article
  on what an interrupted save costs.
* `2a8c91c` — Release 0.2.7.

**Threat model:** unchanged from [`THREAT_MODEL.md`](THREAT_MODEL.md). In scope: theft of
or tampering with the on-disk vault files, a crafted vault, a hostile merge source,
malicious paths and filenames, a local multi-user filesystem, and secrets lingering in
memory or on disk. Out of scope: network attacks, and an attacker already running as the
user with the vault unlocked in RAM.

**What this round deliberately went after that the last one did not.** Round 2 of
2026-07-29 swept two commits that could not reach the crypto — a printed version string.
This round is the opposite case: `fb0873a` changes the **untrusted-input parser**
(`scan_volume`), adds a **new on-disk file**, and adds a **new path into the recovery
code that runs when a manifest is lost**. All three are in the part of the program where
this project's failures have historically lived. The round was aimed at four questions:

1. Can the resync admit anything that is not an authentic frame, or be made to run long?
2. Does the new spare copy create a rollback, a stale-index, or an old-key-at-rest path?
3. Is the redundancy setting handled identically on every path into the store —
   including a read-only open?
4. Did the release process itself do what it is supposed to?

**Result: one Medium and four Low.** The Medium (A-1) and one Low (A-2) are defects in
the code this session shipped as 0.2.7, found by asking question 3 and question 1
respectively. Both are now fixed with regression tests, and **both are in released,
tagged code** — see *Release impact*. The remaining three are a supply-chain advisory
that had never been triaged (A-4), a process gap that let the previous round's L-3 recur
unnoticed through three releases (A-3), and a function with no test coverage at all,
caught by mutation testing (A-5).

The cryptographic core, the key derivation, the on-disk format, the record parsers, the
single-writer lock and the read-only gate on the *record* APIs all came through clean, as
in the three rounds before this one — alongside **86,463,058 fuzz executions with zero
crashes** across all six targets.

Worth stating plainly, since it is the most useful sentence here: this round audited code
written earlier in the same session, and found two defects in it, one of which defeats a
security property the threat model states in writing. Fresh code is where the findings
were, which is exactly where the round was pointed.

## Findings

### A-1 — a READ-ONLY open deletes files in the vault folder (Medium, read-only gate)

`crates/vaultis-core/src/vault.rs:511` (`open_inner`) and
`crates/vaultis-core/src/storage.rs` (`VolumeStore::set_redundancy`)

**What the code does.** `open_inner` hands the store the redundancy depth on every open:

```rust
storage.set_redundancy(vault.settings.redundancy);
```

and `set_redundancy` treated a depth of `0` as an instruction to clean up:

```rust
pub fn set_redundancy(&mut self, depth: u32) {
    self.redundancy = depth;
    if depth == 0 { self.drop_manifest_mirrors(); }   // fs::remove_file per partition
}
```

So opening a vault whose saved setting is `0` **deletes every `manifest.<N>.mirror` on
disk** — and `open_inner` calls this regardless of `read_only`.

**What it must do.** A read-only open must not write. The three statements immediately
above this one all consult the flag: the write lock is taken only when writable
(`vault.rs:474`), `recover_pending_rekey` refuses in read-only (`:476`), and
`sweep_stale_temps` is explicitly gated (`:480`). This is the project's recurring
*guard-asymmetry* shape, and the new line is on the wrong side of it.
[`THREAT_MODEL.md`](THREAT_MODEL.md) also documents read-only opens as leaving no trace —
that is what makes the "Last opened" line meaningful as tamper evidence.

**The concrete input that separates them.** A vault with spares on disk while the saved
setting is `0`. `OpenVault::set_redundancy` writes the spares *before* `save()`, so a
save that fails leaves exactly that state:

```rust
crate::fault::fail_at("vault.write", 1);
let _ = v.set_redundancy(2);          // spares reach disk; the setting does not
crate::fault::clear();
// manifest/manifest.0.mirror exists, settings.redundancy == 0
OpenVault::open_with(path, b"a", b"b", true).unwrap();   // READ-ONLY
// manifest/manifest.0.mirror is gone
```

Reproduced by `vault::tests::audit_a1_read_only_open_must_not_delete_manifest_spares`,
which fails on `fb0873a` and passes after the fix.

**Severity: Medium, and why.** It defeats the read-only guarantee, which is a property
the program states and an heir relies on: the desktop opens read-only *by default*, and
the mobile app (`vaultis-ffi/src/lib.rs:436`, `open_read_only`) is read-only always — so
the most common way this vault is opened is the way that writes. It is not High because
nothing unique is lost: the deleted files are by definition redundant copies, the primary
manifest and every document are untouched, and the vault opens normally afterwards. It is
not Low because it is a security-boundary bypass rather than a robustness wart, and it
silently removes protection the user explicitly turned on.

**Fix.** `set_redundancy` now records the depth and nothing else; removing spares is an
explicit separate call (`drop_manifest_mirrors`) that only write-gated paths make —
`OpenVault::set_redundancy`, which checks `read_only` first, and `commit_manifest`, which
is only reachable from `put`/`remove`. The read-only guarantee no longer depends on
remembering to check a flag at the call site, which is the same "make it unrepresentable"
treatment the previous round applied to its L-1.

**Regression tests.** `audit_a1_read_only_open_must_not_delete_manifest_spares` (the
reproduction above) and `storage::tests::setting_the_redundancy_depth_never_deletes_anything`.
`turning_redundancy_off_removes_the_manifest_spares` was updated to the corrected
contract: the next manifest commit clears the spare, not the act of recording the depth.

### A-2 — a crafted or badly damaged volume makes a rebuild read ~8 GiB (Low, robustness)

`crates/vaultis-core/src/storage.rs` (`resync_to_next_frame`)

**What the code does.** When a frame will not decrypt, the scan walks forward looking for
one that authenticates, capped at `RESYNC_ATTEMPTS = 128` decrypt attempts per damaged
region. The cap bounds how *many* attempts happen but not how *big* each one is, and
`read_frame_at` reads the whole advertised frame — up to `MAX_DOC_SIZE` (64 MiB) — before
the AEAD rejects it. A volume whose bytes decode as plausible large lengths therefore
costs up to 128 × 64 MiB ≈ **8 GiB of reads per damaged region**.

**What it must do.** Bound the work, in bytes as well as in attempts. Before this change
the scan stopped at the first bad frame, so the same input cost one read; the resync is
what multiplied it.

**The concrete input that separates them.** 64 MiB of the repeating pattern
`00 00 30 00`, so every 4-byte window decodes to a 3 MiB in-range length, with the
manifest removed to force a rebuild:

```
rebuild of a 64 MiB crafted volume: 3.316 s      (before)
rebuild of the same volume:         0.427 s      (after)
```

It is reachable without an attacker: ordinary corruption of a wide region of a large
volume produces plausible lengths at roughly 1.5% of offsets, which is more than enough
to fill the attempt cap. **The fuzzer cannot reach it** — libFuzzer inputs are kilobytes,
and the cost scales with file size, which is why 86 M executions reported
`slowest_unit_time_sec: 0` while this sat in the code.

**Severity: Low, and why.** No data is lost, nothing is corrupted, no secret escapes, and
the operation completes — it is a slow path on recovery from an already-damaged vault. It
is worth fixing rather than noting because the user-visible symptom is a vault that
appears to hang while opening, exactly when they are already frightened about their data.

**Fix.** `RESYNC_READ_BUDGET`, set to `2 * MAX_DOC_SIZE`, bounds the bytes a walk spends
on failed attempts. The test is on what has *already* been spent, never on how big the
next candidate is — refusing a large candidate would lose exactly the frame the resync
exists to find — so the overshoot is one frame and only a run of large failures is cut
off. Two documents' worth rather than one, because the bytes a walk crosses on the way to
a good frame are damaged or random, and a budget near one document's size can be
exhausted by an unlucky run of plausible lengths in that garbage before reaching a
legitimate maximum-size frame. That was not theory: an 8 MiB budget made
`the_resync_budget_still_recovers_a_large_document` fail intermittently, because the
bytes being walked are a frame's random nonce and ciphertext.

**Regression tests.** `a_crafted_volume_cannot_make_a_rebuild_read_unboundedly` asserts
the bound by **counting the bytes the scan reads** through a `Read + Seek` wrapper, not by
timing it — the bound is a property of the code, and a wall-clock assertion measures the
disk and whatever else the machine is running (it failed under the load of this very
audit's mutation run). `the_resync_budget_still_recovers_a_large_document` pins the other
direction: a 12 MiB document after damage that destroys the preceding frame's length
prefix is still recovered.

### A-3 — the previous round's L-3 mitigation has never fired (Low, process)

`scripts/release.sh:238-248`, `fuzz/Cargo.lock`

**What the code does.** `fuzz/` is a detached workspace whose lockfile records the path
dependency's version, so a release bump never reaches it and the next `cargo fuzz build`
rewrites it — dirtying the tree mid-audit. Round 2 of 2026-07-29 filed this as L-3 and
fixed it by adding a **warning to `scripts/release.sh`**.

**What it must do.** Actually fire. At the start of this round `fuzz/Cargo.lock` recorded
`vaultis-core 0.2.4` — three releases stale (0.2.5, 0.2.6, 0.2.7), all cut after the
warning was added. The mitigation was placed in a script that none of those releases ran;
0.2.7 was cut by hand in this session, which is how the gap became visible.

**Severity: Low, and why.** No security impact — it is a stale version string in a lock
file for a workspace that ships nothing. It is filed because a control that has never
executed is worse than no control: it reads as coverage on the next round.

**Fix.** A check in CI's supply-chain job comparing `fuzz/Cargo.lock`'s `vaultis-core`
version against `crates/vaultis-core/Cargo.toml`, failing the build on drift. CI runs on
every push regardless of how a release was cut, so it does not depend on the path taken.
`fuzz/Cargo.lock` is committed at 0.2.7.

### A-4 — an unsoundness advisory had never been triaged (Low, supply chain)

`.cargo/audit.toml`

**What the code does.** `cargo audit` reported `RUSTSEC-2026-0221` (`event-listener`
5.4.1, `!Send` tags crossing thread boundaries via `StackSlot`, dated 2026-07-13) as an
allowed warning. `audit.toml`'s own header states the policy — *"Ignored advisories, each
with its justification"* — and carries three entries that follow it. This advisory has no
entry and no justification; it was passing as an unexplained warning, and appears in none
of the nine prior audit documents even though it predates two of them.

**Severity: Low, and why.** It is an unsoundness, not an exploitable vulnerability,
reachable only through the desktop GUI's Linux accessibility stack
(`eframe → egui-winit → accesskit_winit → accesskit_unix → zbus → async-broadcast`), and
it requires a specific misuse pattern by the consuming crate. Filed for the process, not
the bug: the project's discipline is that every surfaced advisory carries a written
justification, and an untriaged one erodes that.

**Fix.** No ignore entry was needed — a fixed version exists.
`cargo update -p event-listener` takes 5.4.1 → 5.4.2, and `cargo audit` now reports no
warnings at all.

### A-5 — `refresh_manifest_mirrors` had no test coverage at all (Low, test coverage)

`crates/vaultis-core/src/storage.rs:306`

**What the code does.** `cargo mutants`, scoped to the release diff, replaced the whole
body of `refresh_manifest_mirrors` with `()` and separately flipped its
`self.redundancy == 0` guard to `!=`. Both mutants **survived** — the whole suite stayed
green with the function doing nothing, and with its guard inverted.

**What it must do.** Be tested. It is the path that restores the spare manifests after a
rekey or a compaction, so "silently does nothing" is precisely the failure that leaves a
vault without the protection its settings claim, discovered only when a manifest is lost
and there is no spare to recover from.

**Severity: Low, and why.** No defect was demonstrated in the function itself — the
finding is the absence of a test, which is how a future defect would go unnoticed.

**Fix / kill-test.** `refreshing_the_spares_covers_partitions_that_already_exist`
exercises both directions: turning redundancy on and refreshing writes the spare for a
partition that already exists (killing the `()` mutant), and refreshing at depth 0 writes
nothing (killing the guard mutant).

## Leads chased and refuted

* **Could the byte-wise resync admit a forged or misaligned frame?** No. A candidate is
  accepted only by passing its AEAD tag, and the AAD binds `vault_id` and `partition`, so
  a frame from another vault or partition fails. A frame nested inside another frame's
  body cannot be found either: document bodies are ciphertext on disk, so a valid inner
  frame never appears in the clear to be scanned for.

* **Could a recovered entry be overwritten by the next append?** No. `end_offset` only
  ever advances past frames that were successfully read, so every entry a scan admits
  ends at or before it; `merge_volume_tail` additionally `max`es the two candidates so the
  append point can never move backwards.

* **Does the spare create a rollback path that resurrects deleted documents?** It can
  reinstate a deleted document's *index entry* — but this is the pre-existing shape of a
  manifest-loss rebuild (documented at `vault.rs:1166`, "a manifest-loss rebuild
  re-admitted a deleted frame"), and the authoritative deletion record is the tombstone in
  `vault.pmv`, which every export, compaction and read path filters on. No new capability.

* **Can a planted `manifest.<N>.mirror` do harm?** No. It is read through the same
  `load_manifest_at` as the live file: `symlink_metadata` rejects a symlink, the read is
  capped at `MAX_MANIFEST_SIZE` and does not follow links, and the AEAD rejects anything
  not written under the vault's key. It is written through the same symlink-safe
  `write_atomic`, and its permissions were measured at `0600`. A garbage spare costs one
  bounded read on a path that only runs when the live manifest has already failed.

* **Are the spares left behind under an old key after a password change?** No.
  `commit_rekey` replaces the whole `manifest/` directory, taking any old-key spares with
  it; the staged store's depth defaults to 0 so it writes none; and a `.manifest.old` left
  by a failed cleanup is reaped by `sweep_stale_temps` on the next writable open.

* **Does `backup` omit the new file?** No. `copy_dir` copies `manifest/` and `volume/`
  recursively, so spares travel with a backup, and symlinked entries are refused. (The
  vault file's own `.mirror`/`.bakN` copies are deliberately *not* backed up — a backup is
  a fresh consistent copy and the next save rebuilds the ring. Pre-existing, unchanged.)

* **Is the stale-spare tail merge quadratic enough to matter?** It is super-linear —
  measured at 25 ms / 48 ms / 132 ms for tails of 500 / 1000 / 2000 entries, from the
  `retain`-per-entry dedupe. Not filed: reaching a tail large enough to hurt needs on the
  order of 100,000 manifest commits each paired with a *failed* spare write, when both go
  through the same `write_atomic` into the same directory.

* **Can the GUI's new `sync_edit_buffer` clobber unsaved work or leak a secret?** No. It
  is tab-scoped, runs only after a successful persist of that tab's own buffer, and
  replaces the buffer with an identical-content clone whose predecessor is zeroized on
  drop. A failed save deliberately does not sync, which is asserted under fault injection.

## Not run, or partial

* **`cargo fmt --all -- --check`** reports diffs in ~50 files across the whole repository,
  including files untouched by this round. The project is deliberately hand-formatted and
  CI has no `fmt` gate (stated in `ci.yml`), so this is expected rather than a finding —
  recorded so the skipped gate is explicit. It was **not** run as a corrective action; a
  repo-wide reformat is not an audit's business.
* **The Windows packaging surface was not verified.** No Windows host was available. The
  0.2.7 release zip was built and published by CI (`release` run 30812166864, success),
  but its SHA-256, the two binaries' subsystems, their DLL imports, and
  `get_vaultis.bat`'s refusal behaviour were not checked locally. If 0.2.7 is treated as a
  shipping release rather than superseded, that check is still outstanding.
* **Mutation testing was partial: 25 of the 77 mutants in the diff.** The run was stopped
  when the machine reached 94% disk (`cargo mutants` rebuilds per mutant, and a full-disk
  linker failure had already broken one build earlier in the day). The 25 tested include
  every mutant `cargo-mutants` generated inside the new `storage.rs` code up to that
  point, which is where both survivors were. The remaining 52 are **untested**, so the
  "no surviving mutant" claim this project has made in previous rounds is *not* claimed
  here — A-5 is what the partial run found, and there may be more in the untested 52.
  Re-run with disk headroom: `cargo mutants --in-diff /tmp/release.diff -p vaultis-core`.
* **`cargo llvm-cov`** was not run this round.
* **Kani proofs, ASan/LSan/TSan, the memory-residue observation and the reproducible-build
  check** were not run — they are the `deep-audit` scope, last exercised on 2026-07-29.
* **CodeQL** has failed on every push since 2026-08-01, including this release. It is not
  a Rust finding: GitHub's default setup cannot autobuild the `mobile/` Kotlin app
  (`no source code seen during build`). Out of scope for this round, but it means the
  repository's code-scanning signal has been red-and-ignored for four runs.

## Release impact

**A-1 and A-2 are in released, tagged code.** `v0.2.7` is published with the Windows
binaries built from it. Neither can corrupt a vault or expose plaintext, and neither
affects a vault whose redundancy setting has never been turned on — which is the default,
so the great majority of vaults are untouched by both. A-1 requires spares on disk with
the saved setting at 0; A-2 requires a manifest to be lost *and* a large volume to be
damaged across a wide region. A follow-up release is recommended but not urgent.
