# Deep Audit — 2026-07-25

A workspace-wide bug hunt and security review (core, desktop GUI/TUI/CLI, ffi, fuzz, and the
dependency tree), run after the rename-to-`vaultis` and merge/launch-directory work landed on
`main`.

**Threat model (unchanged from [`AUDIT_2026-07-03.md`](AUDIT_2026-07-03.md)):** a standalone,
OFFLINE two-password encrypted estate vault. In scope: theft of / tampering with the on-disk
vault files, a crafted vault / **hostile merge-source vault** / **portable vault handed to the
user** / document fed to open/merge/import/extract, malicious paths/filenames/record content, a
local multi-user filesystem (permissions, symlinks, TOCTOU), and secrets lingering in
memory / on disk / in the terminal. Out of scope: network attacks (the app opens no sockets),
and an attacker already running as the user with the vault unlocked in RAM.

**Result:** no Critical findings. One **High** finding (a confidentiality issue: untrusted vault
media choosing where cleartext exports are written), one Medium, and four Low/defence-in-depth
findings were confirmed and fixed. The cryptographic core, the on-disk format, the parsers, and
the crash-safety machinery came through clean.

---

## Findings fixed

### H-1 — A vault's own `prefs.json` could choose where this machine writes cleartext (High, confidentiality)

`crates/vaultis-desktop/src/lib.rs`

The desktop prefs layer reads `<config dir>/vaultis/prefs.json` and falls back, key by key, to a
`prefs.json` sitting in the **vault root** — a deliberate feature so a self-contained / portable
vault carries its own UI defaults to a new machine (see
[`SELF_CONTAINED_BACKUP.md`](SELF_CONTAINED_BACKUP.md)).

That fallback file ships with the vault media, so its author is *whoever produced the vault* —
a USB stick, a restored archive, a vault handed to an heir, a shared network folder. Two of the
keys it could set are security decisions, not cosmetics:

* **`export_dir`** — the destination every front-end Export button writes to. That is the
  per-tab CSV, which carries **every account and portal password in the clear**, and every
  decrypted document. With no `export_dir` in the user's own config file (a fresh install, or a
  user who never set one), the vault's value won — silently, and shown in Config as if the user
  had chosen it. A crafted vault could point it at a world-readable directory, a cloud-synced
  folder, a Windows UNC share, or the vault directory itself.
* **`reveal_all_default`** — opens every password-bearing tab **unmasked**, turning off the
  app's shoulder-surf / screen-share protection without the user asking.

**Fix.** The vault-root side is now filtered through a deny-by-default allowlist,
`VAULT_FALLBACK_KEYS`, before the merge. Only the two purely cosmetic view keys
(`group_assets_default`, `group_accounts_default`) may travel with a vault; `export_dir` and
`reveal_all_default` join `vault_root` / `last_vault` as config-dir-only. `theme` was already
read from the config dir directly. Regression test:
`a_foreign_vaults_prefs_cannot_choose_where_cleartext_exports_go`.

### M-1 — GUI/TUI exports had no "outside the vault folder" guard (Medium, confidentiality)

`crates/vaultis-desktop/src/{lib,gui,ui}.rs`

The CLI has refused to write cleartext into the live vault directory since the
`extract` / `export-tree` / `compact --backup-dest` guards: plaintext stranded next to
`vault.pmv` is swept up by the user's next backup or folder sync of that vault. The windowed
and terminal front-ends export to the Config-screen directory and had **no such check**, so the
same CSV (every password) and the same decrypted documents could land inside the vault folder.
The project's own test suite was doing exactly this — every export test wrote into the vault
directory, which is how the gap stayed invisible.

Combined with H-1 this was directly reachable: a foreign vault could set `export_dir` to its
own folder, so an export would deposit the user's cleartext passwords where the vault's owner
collects them on the next sync.

**Fix.** `dest_inside` / `resolve_existing` moved out of the `vaultis` binary into the library
so all three front-ends share one definition, and a new `checked_export_dir` performs the unset
+ inside-the-vault check in one place. Both front-ends call it at every export site *and* when
the directory is set in Config, so the user is told immediately rather than at the first export.
`dest_inside` resolves both sides through the filesystem, so an export directory named through a
symlink pointing back into the vault is caught too. Regression tests:
`exports_into_the_vault_folder_are_refused_in_gui` / `..._in_tui`,
`checked_export_dir_refuses_unset_and_anything_inside_the_vault_folder`,
`checked_export_dir_sees_through_a_symlink_pointing_back_into_the_vault`.

### M-2 — `read_prefs_obj` had the stat-then-`fs::read` symlink/size gap (Medium, DoS)

`crates/vaultis-desktop/src/lib.rs`

The prefs reader pre-checked with `symlink_metadata` (rejecting a symlink, capping at
`MAX_PREFS_SIZE`) and then read with `std::fs::read`, which **follows symlinks and allocates
without bound**. This is precisely the pattern the core crate calls out and closes in
`storage::load_manifest`, `vault::read_capped` and `vault::read_bounded`: the stat is a separate
syscall from the read, so a file swapped for a symlink to `/dev/zero` in between — or one that
simply grows — bypasses both guards. It matters here rather than being purely theoretical
because the vault-root fallback reads this file from untrusted, possibly removable or
network-mounted media, at UI startup.

**Fix.** The read is now `read_bounded_nofollow` — `O_NOFOLLOW` open, `take(max + 1)` — so the
symlink is refused at the open and the allocation can never exceed the ceiling. Regression
tests: `read_bounded_nofollow_enforces_the_exact_cap`,
`prefs_read_does_not_follow_a_symlink_even_past_the_stat`.

### L-1 — `write_prefs_obj` wrote through a symlink and left a truncation window (Low)

`crates/vaultis-desktop/src/lib.rs`

`std::fs::write` opens the path directly: it follows a symlink planted at `prefs.json` and
truncates-then-writes in place, leaving a window where a concurrent front-end reads a
half-written file and a crash leaves it truncated.

**Fix.** Atomic `O_EXCL` 0600 temp sibling → rename, matching every other writer in the project;
a rename *replaces* a planted symlink instead of writing through it. Regression test:
`write_prefs_obj_replaces_a_symlink_instead_of_writing_through_it`.

### L-2 — `rebuild_manifest` bypassed the manifest entry cap (Low, availability, defence-in-depth)

`crates/vaultis-core/src/storage.rs`

`MAX_MANIFEST_ENTRIES` is enforced by `load_manifest` (fails closed with `TooLarge`), by
`target_partition` (rolls to a fresh partition), and by `import_tree`. The manifest-loss
**rebuild** path did not: `scan_volume` is infallible by design — it returns whatever intact
prefix it found — so it was the one way an over-cap manifest could enter memory. From there the
next `put`/`remove` in that partition would commit it, and every later open would hit
`load_manifest`'s `TooLarge`, which `VolumeStore::open` does **not** treat as rebuildable: an
otherwise-intact vault would be permanently unopenable.

Not reachable for a vault this code produced (`target_partition` keeps every partition under the
cap), so this is the read side being unable to admit what the write side would refuse — but a
guard enforced at three of four sites is not a guard.

**Fix.** `reject_over_cap` applies the same cap, with the same error variant, to a rebuilt
manifest. Fails closed; destroys nothing. Regression tests:
`a_rebuilt_manifest_obeys_the_same_entry_cap_as_a_stored_one`,
`rebuild_from_a_volume_still_succeeds_under_the_cap`.

### L-3 — `fmt_money` invented a figure for a non-finite total (Low, correctness)

`crates/vaultis-desktop/src/lib.rs`

`records::parse_approx_value` rejects a non-finite *field*, but the Summary tab **sums** many
finite values, and two near-`f64::MAX` entries add to `+inf`. `f64 as u64` saturates in Rust, so
an infinite total rendered as the literal `$18,446,744,073,709,551,615` and `NaN` as `$0` — a
fabricated number presented as a real one in a financial view.

**Fix.** A non-finite total renders `$—`. Regression test:
`fmt_money_reports_a_non_finite_total_as_out_of_range`.

## Reviewed and found sound (no action)

* **Dependencies.** `cargo audit`: **0 vulnerabilities** across 599 crates. `cargo deny`:
  advisories / bans / licenses / sources all ok.
* **Crypto core** (`crypto.rs`). Argon2id with header-stored, bounds-validated parameters;
  chained two-password derivation salted by `k1`; XChaCha20-Poly1305 with the **entire** header
  (magic, version, params, salt, nonce) as AAD; known-answer tests pinning the KDF, the published
  draft-irtf-cfrg-xchacha vector, and frozen project vectors. The per-page refcounted `mlock`
  and the zeroization discipline hold up.
* **Parsers.** Header, frame plaintext, manifest JSON and the volume scan are bounds- and
  overflow-checked ahead of every allocation, with `checked_add` on every offset; all five
  libfuzzer targets were re-run with no crashes.
* **Terminal-escape injection from untrusted record content.** Merged/imported record fields are
  copied verbatim, but ratatui's `Buffer::set_stringn` (which `set_span`/`set_line` delegate to)
  filters control characters out of every rendered grapheme, and the merge-preview labels the
  user authorizes are `records::display_safe`d. The CLI merge preview prints the sanitized label.
* **History secret masking.** `detail_is_secret` covers exactly the five `*password` fields, and
  `display_detail` is applied at every display site — GUI, TUI and the FFI `map_change`.
* **FFI** (`vaultis-ffi`). Wrong-password and corrupt-vault collapse to one variant (no
  correct-password oracle, `ArchiveMismatch` and `TooLarge` included); host-owned password
  buffers are bound in `Zeroizing` so an unwind still wipes them; a poisoned mutex is recovered
  via `into_inner` rather than panicking across the boundary.
* **Password generator.** Rejection sampling over a 64-bit draw (no modulo bias, and no accept-
  zone collapse for large `n`), pre-sized `Zeroizing` buffer, Fisher-Yates over `uniform(i + 1)`.
* **CSV export.** Leading `=`/`+`/`-`/`@` are quote-prefixed against formula injection, and every
  cell goes through `display_safe` first, so control and bidi/zero-width characters cannot break
  the row or spoof the rendering.
* **No external-viewer / temp-file document path.** The front-ends never write a decrypted
  document to a temp file to hand to another program — a common leak vector in this class of app,
  absent here by design.
* **`.rekey` staging planted by a local attacker.** An attacker who can write the vault directory
  could plant a staging tree with a `READY` marker and have the next writable open roll it
  forward. Considered and **accepted**: that attacker can already overwrite `vault.pmv` directly,
  so it grants no new capability, and the symlink-escape variants are already closed by the
  `O_NOFOLLOW` / rename discipline throughout.
